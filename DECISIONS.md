# Decisions

Non-obvious technical choices, newest at the bottom. One entry per decision: what, why, trade-off.

## 2026-10-22 Monorepo scaffold

- **pnpm workspaces, no build step.** `@epidle/core` exports `src/index.ts` directly. Server and CLI run with `tsx`, web with Vite, `tsc` only type-checks (`noEmit`). No "forgot to rebuild core" bugs. Trade-off: production server also runs through `tsx`; add a bundle step if startup time or deploy ever needs it.
- **Biome instead of ESLint + Prettier.** One dependency, one config, lint and format, fast. Markdown and the lockfile are excluded from formatting. Trade-off: fewer plugins than ESLint, nothing we need is missing.
- **Core purity enforced by tooling.** `packages/core/tsconfig.json` has `"types": []` (no Node globals). A Biome override bans `Date`, `performance`, `setTimeout`, `setInterval`, `fetch`, `process`, `console` in `packages/core/**`. Not covered: `Math.random`. Plan: a seeded RNG passed in when game logic needs randomness.
- **better-sqlite3 rather than `node:sqlite`.** `node:sqlite` is still experimental on Node 22. better-sqlite3 is synchronous (simple code, fast for a single-process server) and ships prebuilt binaries. pnpm 10 blocks install scripts, so it is allow-listed in `pnpm-workspace.yaml`. DB opened in WAL mode with foreign keys on.
- **`@types/node` pinned to 22** to match the runtime in `.nvmrc`, so we can't use APIs that don't exist at runtime.
- **API under `/api`**, Vite proxies it in dev: no CORS config needed for the web client.
- **One root Vitest config** with `projects`, so `pnpm test` covers every package. Web and CLI have no tests yet; adding jsdom or ink-testing-library is deferred until there is UI logic worth testing.
- **No dotenv.** Config comes from env vars; Node 22 `--env-file` covers local `.env` if needed.
- **Server binds to `127.0.0.1` by default.** Set `HOST=0.0.0.0` behind a reverse proxy or in a container.
- **TypeScript 7** (native compiler) was the latest at scaffold time. Options used are the standard strict set, nothing TS 7 specific.

## 2026-10-22 Game core and balance

- **Flow model, not a tick loop.** `computeRates(state)` gives constant rates (LoC/s, EUR/s, bugs/s) between two events; `advance(state, seconds)` integrates them exactly, segment by segment, the only events being level-ups. Result: `advance(s, a + b)` equals `advance(advance(s, a), b)`, the server can catch up hours of absence in one call, and there is no tick-size drift between server and clients.
- **Pipeline.** LoC go through the stages in order. A stage processes at most `instances x throughput x speed(strictness)`; the overflow ships right away at the value of the last stage it passed, with its bugs. Quality = 1 - bug density, revenue = LoC x value x quality. A stage with no instance ends the pipeline.
- **No debt spiral by construction.** Production never depends on money, and every dev, at every level, earns more shipping raw buggy code than their salary (asserted in `config.test.ts`). Intents refuse to spend money the player doesn't have. Money can still dip below zero if a player sends most devs to training at once (still paid, writing nothing) or buys moulis with nothing to check, but income stays positive as soon as they work again. No bot ever went below 7 EUR.
- **Tiers unlock on cumulative revenue** (the season score), with the exact unlock time recorded in the state for badges and stats.
- **Mechanics added on top of CLAUDE.md** (each one came out of the simulation, see the PR for the numbers):
  - `train(dev, targetLevel)` queues several levels, paid upfront, the dev stays in the room. Without it an 8-minute Piscine leaves the room empty for 8 h for a casual player: the casual bot made 17% of the hardcore score, 65% with the queue.
  - Mouli versions (`upgradeMouli`): x2 throughput per version, x3 cost. Production is multiplied by up to 2048 by training; with instances alone the bots needed 8000+ instances per stage.
  - Training rooms are bought (`buyRoom`), x1.5 cost each, max 50.
- **Piscine is 8 min, not 10.** With 10 min and x2 per level, Légende takes 14.2 days of non-stop training, more than the season. With 8 min it is 11.4 days: reachable only by someone who keeps one dev in a room from day 0, which makes it a real achievement. No bot reaches it (max level 9).
- **What drives growth.** Training time and perf both double per level, so a busy room adds the same income per second whatever level it trains: growth is roughly rooms x time. Rooms are the engine, devs are what you put in them, moulis turn their code into money.
- **Known limit: money stops being the constraint around day 4 for active players.** A room's value is bounded (it can only train for the time left in the season) while money grows with the company, so after day 4 active bots can afford everything worth buying and only wait for trainings to end. Decisions remain (who to train, how far, strictness, pipeline), and nobody is maxed before day 12. Tried and rejected: a multiplicative "equipment" money sink. It keeps money useful until day 6-9, but scores blow up to 1e13-1e14, mouli instances to thousands, and the 30-min bot beats the 2-min one.
- **Bots are a measuring tool, not an AI opponent.** Greedy "best payback first", they price hires and training at the current average value per LoC (otherwise a full pipeline makes training look worthless), price a room by its reuse over the rest of the season, queue trainings until their next visit, and save for a better action if it becomes affordable before their next visit.

## 2026-10-22 Server, auth and seasons

- **The server does the OIDC exchange (backend for frontend).** Web: the server creates the PKCE verifier, state and nonce, redirects to Microsoft and redeems the code on `/api/auth/callback`. CLI: the server calls the device code endpoint and the CLI polls the server with an opaque handle. Clients only ever hold an Epidle session token (httpOnly cookie for the web, bearer for the CLI): no Microsoft token in browser JS, one verification path, sessions revocable by deleting a row.
- **Tenant restriction is triple:** tenant-specific authority (never `common`/`organizations`, config refuses a non-GUID tenant), id_token issuer pinned to that tenant, and `tid` claim checked. Signature checked with `jose` against the tenant JWKS. Only `oid` is kept; name and email in the token are ignored.
- **Login CSRF:** the web login state is also stored in a short httpOnly cookie, so a callback only works in the browser that started it. States and device handles are single use and expire (10 min / Microsoft's expiry).
- **Sessions:** 256-bit random tokens, only their sha256 is stored, fixed 30-day expiry, no refresh.
- **Pseudo:** ASCII `[A-Za-z0-9_-]{3,16}`, unique ignoring case, required before playing, can be changed. ASCII keeps terminal tables aligned and avoids look-alike Unicode names. No moderation yet.
- **Any Epitech account can play, whatever the campus.** The game targets Lyon, but the Epitech tenant covers every campus and the id_token has no campus claim. Accepted by the project owner: a player from another campus is welcome and simply shows up in the leaderboard. No Graph call, nothing stored beyond the oid.
- **A company starts on the player's first visit**, at the current season time. Late joiners have less time, the season ends for everyone at the same moment (the score is cumulative revenue, so this is the fair version).
- **Season rollover is lazy and scheduled.** Every request calls `currentSeason(now)`, which closes a finished season (every company advanced to the exact end time, frozen) and opens the next one; a job does the same every minute plus cleanup. Seasons follow each other with no gap; after a downtime longer than a season, the next one starts now instead of creating empty seasons.
- **Leaderboard is live:** before answering, every company of the season is advanced to now, at most every 30 s (the job also does it every minute). All-time = sum of every season, including the current one. Alternative if it rewards veterans too much: best season.
- **Intents:** JSON schema first (Ajv with no type coercion and no stripping of unknown fields: a stray `time` or `money` is a 400, not ignored), then the core rules (422 with the French message and the current state). `count` (1-100) on repeatable intents so "hire x10" is one request. Each intent carries a client `requestId`, kept 24 h: a replay is a 409 and changes nothing. Processing is synchronous and in one transaction, so concurrent requests of the same player cannot interleave.
- **Rate limits** (in-memory, keyed by player when logged in since the whole campus may share one IP, by IP otherwise): 300 req/min global, 30 intents per 10 s, 120 auth req/min per IP, 30 device polls/min per login. The plugin runs on onRequest, before validation and auth checks (so invalid and anonymous spam counts), after the global hook that resolves the session, and must be registered before the routes. Device polling is keyed by the body, so that route uses preHandler. Quirk of its in-memory store: in a burst that goes over the limit before any response, every request of the burst is refused. Acceptable for spam.
- **One server process.** SQLite in sync mode and the in-memory rate limit store both assume it. Enough for one campus; Redis store and Postgres would be the path if that ever changes.
- **Migrations:** an append-only list of SQL scripts, the version is `PRAGMA user_version`, each runs in a transaction on start. A database newer than the server refuses to open.

## 2026-10-22 Web client

- **Polling plus local projection, not SSE.** The state only changes on intents (which return the new state) and with time, which `advance()` from core computes exactly. So the client polls `GET /state` every 15 s (visible tab only, plus on focus and at season end) and extrapolates the last response 4 times per second. SSE would need a long-lived connection per player and server push logic for no visible gain. Cost: up to 15 s to see something that did not come from this tab (another tab, the CLI).
- **Projection uses a monotonic clock** (`performance.now()` since the response), never the local date: a wrong or changed PC clock cannot shift the display. Out-of-order responses are dropped by comparing `serverTime`.
- **Local precheck of intents.** Before sending, the client runs the same core intent on the projected state. If it is refused (no free room, not enough money, locked) the French message shows right away and nothing is sent. The server still validates everything; the only risk is refusing locally an action that would have passed a few milliseconds later, the same rule that greys out its button.
- **Shop prices come from running the core intents**, so "x10" shows the exact sum of rising prices the server will charge, and the "max" quantity is what the money pays for (capped at the server limit of 100).
- **Hash routes** (`#/boutique`, `#/joueur/<pseudo>`): no server or hosting config, and build links can be pasted in a chat.
- **Shortcuts read digits from `event.code`**: on AZERTY, "1" needs Shift, so `event.key` would be "&". Letters use `event.key` so they follow the layout. Hints are hidden on touch screens.
- **No UI library, no router, no font download.** Panels are CSS boxes with the title on the border, bars are block characters, the font is the system monospace with ligatures off. Dark only: it is a terminal.
- **Language choice stays in `localStorage`.** It is cosmetic (CLAUDE.md), so not worth a column on the server.
- **Tests cover the logic, not the components:** formatting, projection, precheck, bulk prices, routes, key mapping and the highlighter run in Vitest without a DOM. Screens were checked in Chromium at 1280 and 375 px. Component tests would need jsdom and testing-library; not worth two dependencies yet.

## 2026-10-23 Terminal client

- **One shared package, `@epidle/api-client`.** Besides the API client it holds everything else both clients need and that has no UI: projection and precheck, shop quotes, French formatting, the cosmetic languages, and the polling hooks under `@epidle/api-client/react`. Splitting it in several packages would add names for no gain at this size. The hooks take the browser-only parts (poll only while the tab is visible) as options, so the CLI just polls.
- **`createApi({ baseUrl, token })`.** The web client keeps its httpOnly cookie (same origin, no token in JS). The CLI sends the session as a bearer, the server already accepted both.
- **Device code flow, proxied by the server** (built with the server): the CLI never talks to Microsoft and only holds an opaque handle, then an Epidle session token. Polling follows the interval the server returns and keeps going through network errors, 429 and 5xx until the code expires.
- **Token storage:** `~/.config/epidle/config.json` (XDG, `%APPDATA%` on Windows), one token per server origin, written atomically with mode 0600. No OS keychain: it would need a native dependency, and the token only gives access to a game, expires after 30 days and can be revoked with `--logout`.
- **https only, except localhost.** `--server http://...` on another host is refused: the bearer would travel in clear text.
- **Opening the browser** uses `xdg-open`/`open`/`rundll32 url.dll`, never `cmd /c start` (which interprets `&` in the URL), and only for an `https:` URL since it comes from the server. No `open` package for three lines.
- **Keyboard:** terminals send characters, not physical keys, so the AZERTY digit row (`&é"'(-è_çà`) maps to digits. Shift+digit cannot be told apart from a digit on every layout, so shop upgrades (`Shift+5-8` on the web) are bought with the cursor (`↑↓ Enter`). Every action the web does with a mouse has a key: training form with the arrows, leaderboard rows with `↑↓ Enter`. A refused action logs its reason instead of a greyed-out button.
- **Layout for small terminals:** two columns from 110 columns, otherwise `Tab` switches between company and pipeline. The screen area has a fixed height and scrolls with `PgUp/PgDn` (Ink `contentOffsetY`) instead of overflowing, which would break Ink's redraw. Panels must not shrink (`flexShrink={0}`), Ink boxes shrink by default and their lines then overlap. Runs in the alternate screen, so quitting restores the terminal.
- **Published as `epidle`, bundled with esbuild.** `npx epidle` needs plain JS: esbuild bundles the CLI with the workspace TS packages into `dist/epidle.js` (86 kB); `ink` and `react` stay regular dependencies, Ink is not meant to be bundled. The package was renamed from `@epidle/cli` to `epidle` and is no longer private. Checked with `npm pack` + `npx ./epidle-0.1.0.tgz`. The default server is still `http://localhost:3000` until the production URL is known.
- **Tests without ink-testing-library:** `renderToString` from Ink renders screens in Vitest for smoke tests; args, settings storage, key mapping and the browser opener are tested as plain functions. Interactive flows (device login, pseudo, shortcuts, scrolling, Ctrl+C) were checked by driving the real CLI in a pseudo terminal against a server with a fake Microsoft.

## 2026-10-23 Weekly modifiers, feed, anti-scripting, deploy

- **A modifier is a set of balance multipliers, not new rules.** `applyEffects` returns a modified `Balance`, and every core function already takes one, so the rules stay in one place and the clients' projection stays exact. Ten knobs, each limited to x0.25-x4: a week spices up the game, it does not rewrite it. The exact effects are shown next to the hand-written description, generated from the numbers.
- **Weeks are season weeks (days 0-7 and 7-14), not calendar weeks.** Seasons don't start on a Monday, and season time is what the core counts in. `advanceSeason` splits `advance` at week boundaries with an explicit week counter (never relies on a float landing exactly on the boundary); a level that ends exactly at the boundary schedules its next level with the old week's duration, the same on server and clients.
- **The rotation is copied into the season when it opens** (`seasons.weeks`). Editing `modifiers.json` mid-season would otherwise change rules players already planned for. Cost: fixing a typo in the current season needs a SQL update. Week k of the server takes `rotation[k % length]`, so the rotation continues across seasons.
- **Simulated before shipping:** each of the 6 shipped modifiers in week 1 or 2, 3 bots. Effects on the score from 0 % (Soldes, Grève: money is not the constraint after day 4, see the known limit above) to +53 % (Rush in week 2, for everyone). Casual/hardcore ratio stays within 45-56 %, no bot below 0 EUR. The all-time ranking sums seasons whose weeks differ: accepted, every player of a season gets the same weeks.
- **Feed events are stored, "first" is computed when read.** Tiers and levels are detected when a company is saved (the previous row is read in the same place), rank changes when scores are refreshed. Several companies are caught up in one refresh, so insertion order is not reach order: the first of a season is the earliest `at` (exact unlock time for tiers, save time for levels). The first ranking of a season sets the baseline without events; with 10 players or fewer there are no top 10 events; cooldowns of 1 h (lead) and 6 h (top 10) per player.
- **Climbers are exact without a weekly job.** Each row keeps the score at the start of the week it was saved in. The first save after a boundary advances the previous save (from before the boundary, and nothing happened since: every intent saves) to the boundary.
- **Copy my build is built client side** from the projection and the rank of the leaderboard, with the shared formatting. Discord code block for the columns, link after it so it stays clickable. CLI: OSC 52 plus the text on screen, since some terminals (and tmux by default) ignore OSC 52. No clipboard dependency.
- **Anti-scripting logs, it does not ban.** Rate limits are the hard limit (route limits added on the state, builds, leaderboard and feed). The rest is a log for a human: what the official clients never do (429, schema-refused intents, replays) and hourly patterns from the intent ids we already keep 24 h (flood, 20 active hours out of 24, timer-like cadence with a coefficient of variation under 0.1). A false positive would ban a student who plays a lot, and the server being authoritative, a bot can only play well, not cheat. Dedup: one row per player and kind per 10 min. Note: a route-level rate limit replaces the global one for that route in `@fastify/rate-limit`, so `/state` no longer counts in the 300/min.
- **Removing a player deletes the user row** and cascades to companies, sessions, intents and feed events; the suspicious log keeps the pseudo. `--ban` stores the Microsoft oid in `bans` (still no name or email). No soft delete: nothing would read it.
- **Backups use SQLite's online backup API** (`db.backup`), consistent while the server writes, unlike copying the file next to its WAL. In the server process, every 6 h and at start, 28 kept: no cron container. Copying them off the machine stays a manual step in the runbook.
- **The server is bundled for Docker** with esbuild, like the CLI (dependencies stay external, `pnpm deploy --prod` installs them). This revisits the scaffold choice of running production through tsx: the image would otherwise carry every dev dependency. `pnpm dev` and `pnpm start` still use tsx.
- **Caddy in front** (second image from the same Dockerfile): automatic HTTPS, static files with immutable caching of hashed assets, `/api` proxy. The server port is not published, so trusting `X-Forwarded-For` is safe.
- **better-sqlite3 is no longer built on install.** Version 13 ships prebuilt binaries for linux/macOS/Windows, glibc/musl, x64/arm64; the build allowed in `pnpm-workspace.yaml` only compiled a copy with node-gyp, which needs Python and a compiler (it broke the Docker build). Moved to `ignoredBuiltDependencies`.
- **Admin commands in English, run next to the server** on the same database (`pnpm admin`, `node dist/admin.js` in Docker). `remove` is a dry run without `--yes`.
